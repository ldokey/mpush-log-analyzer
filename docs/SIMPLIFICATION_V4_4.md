# V4.4 — 필요한 문제부터 보는 단일 Agent 로그 조사

## 사용 순서

앱을 열면 **1 자료 가져오기**부터 시작합니다. 파일·압축 업로드 또는 등록 폴더를 선택하고, 한 Agent의 파일임을 확인한 뒤 **분석 시작**을 누릅니다. 업로드 파일 목록·분류는 자동으로 준비합니다. 문의 번호/고객사 정보는 선택이며 나중에 기록할 수 있습니다. 분석 완료 후 **2 분석 결과**로 이동합니다.

상단 순서는 **자료 가져오기 → 분석 결과 → 문의·기록 → 내보내기**입니다. 선택한 단계만 실행하므로 아직 보지 않은 분석/사례/보고서 화면을 함께 만들지 않습니다. 기존 분석을 열 때는 자료 가져오기의 **기존 분석 열기** 또는 2단계를 선택합니다.

결과 안의 기본 화면은 **핵심 요약 / 오류 원인 / 메시지 검색 / Job·성능** 네 개입니다. 전체 이벤트/SQL·기존 상세 조사 도구는 **전체 근거 보기** 또는 **고급 분석 도구 열기**에서 접근합니다. 데이터는 삭제하지 않습니다.

## 각 화면에서 볼 내용

### 핵심 요약

가장 먼저 명시적인 오류의 의미와 실패 작업, 반복 기록 수, 확인할 근거를 보여줍니다. 정상 빠른 SELECT, 대상 0건의 빠른 완료 Job, 정상 헬스체크 및 일반 기록은 기본 목록에서 접습니다. 몇 건을 접었는지 표시하고 원본·전체 이벤트는 보존합니다.

DB 실패·미완료, 기본 1,000ms 이상 SQL, 기본 10초 이상 Job, RUNNING/ABNORMAL, 기동·종료 등은 별도 확인 목록에 남습니다. Job 지연 하한은 조사 구간 입력에서 조정할 수 있습니다. 모든 빠른 SELECT가 불필요하다는 뜻은 아니며, **select completed는 반환행 0건의 증거가 아닙니다.** 결과 행수를 알 수 없는 경우 그대로 미확인으로 남깁니다.

오류 기록이 많아도 추가 지연 작업 목록의 표시 상한을 모두 소비하지 않도록 오류 묶음과 작업 목록을 분리합니다. 요약은 최대 300개 오류 묶음과 500개 작업을 보관하고 대표 작업 20개를 먼저 보여주며 생략 수를 공개합니다. 더 자세한 조사는 구간을 좁히거나 전체 근거를 사용합니다.

### 오류 원인

LSysException 같은 상위 래퍼나 unspecified를 제목으로 삼는 대신 다음을 구분합니다.

- **관측 사실:** 연결 단계 시간초과, 응답 읽기 시간초과, 연결 거절, 풀 대기, DNS/TLS, DB 오류 등
- **실패 작업:** 헬스체크/설정 확인, 결과 수신, 파일 전송, DB 등 명시적인 스택 근거
- **해석 한계·다음 확인:** 원인 후보 중 무엇을 추가로 확인해야 하는지

예를 들어 `LSysException → ConnectTimeoutException → SocketTimeoutException: connect timed out`와 `httpClientToTSMSHealthCheck`가 있으면 **헬스체크 중 서버 연결 시간 초과**로 표시합니다. 로그에 포트가 명시되면 숫자 포트도 보여줍니다. 방화벽 차단을 자동 확정하지 않습니다. 최하위 예외·원인 연결·시각·줄번호는 보조 근거로 유지합니다.

예외 클래스가 없는 연결 실패 문구도 분류할 수 있습니다. 인접 1초 이내의 명시적인 오류 프리앰블과 바로 뒤 래퍼 스택만 연결하며, 다른 시각의 독립 오류를 임의로 원인 체인으로 묶지 않습니다. 본문 안의 가짜 오류 문구는 원인으로 사용하지 않습니다.

같은 유형을 묶은 것은 같은 서버/요청의 동일 사고라는 뜻이 아닙니다. 제출 자료만으로 판단할 수 없으면 **오류 상세 원인 미확인**으로 남기고 필요한 근거를 안내합니다.

### 메시지 검색

**MESSAGE_SEQNO를 입력하고 debug에서 찾기**를 실행합니다. SERVICE_SEQNO는 선택입니다. 실제 Agent의 다음 구조를 읽습니다.

- 대문자/밑줄 또는 camelCase 키값: `MESSAGE_SEQNO`, `messageSeqno`, `SERVICE_SEQNO`, `serviceSeqno`
- JSON 객체 바깥쪽의 식별 필드
- `LMultiData Result`의 `messageSeqno/serviceSeqno` 열과 개별 행

기본 대상은 **debug**입니다. 필요하면 info·err를 함께 선택할 수 있으나 **dbwrap은 메시지 검색 대상이 아닙니다.** SQL 문장의 조건값을 메시지 발송 근거로 사용하지 않습니다.

메시지 번호가 일치하지만 같은 기록에 서비스 번호가 없으면 버리지 않고 **서비스 미확인**으로 표시합니다. 검색창에 입력한 서비스 번호로 빈 값을 채우거나 확인된 서비스 기록과 합치지 않습니다. 서비스 번호가 명시되어 있으나 입력값과 다르면 제외 건수를 보여줍니다.

`AGENT_MESSAGE_SEQNO`는 원 `MESSAGE_SEQNO`와 별도 번호입니다. 검색의 **번호 종류**에서 명시적으로 선택합니다. 시각이 가까운 다른 기록에서 식별값을 가져와 연결하지 않습니다.

표에 나타나는 **번호 발견 / 요청 수락 / 결과 코드 관측 / 서비스 미확인**을 구분합니다. `RESPONSE_CODE=S`가 있는 결과 표도 요청 수락일 뿐 최종 수신 성공이 아닙니다. 명시적인 결과수신 문맥과 SEND_RESULT_CODE1/2가 있어야 결과 코드로 표시합니다. 원 발송·문자 대체를 분리하고 상반 결과를 마지막 값으로 덮어쓰지 않습니다.

결과는 발견한 **기록 수**이며 고유 발송 건수나 최종 성공률이 아닙니다. 서비스 없는 기록은 서비스별 최종 성공 집계에 넣지 않습니다. 날짜 없는 기록은 별도 표시할 수 있지만 날짜·전후 관계를 만들어내지 않습니다.

검색 목록은 25건씩 조회하고 최대 5,000개 기록을 표시합니다. 큰 표는 행 단위로 읽어 200행 이후의 메시지도 찾습니다. 숫자/문자 식별값의 완전 일치만 허용합니다. 본문, SQL, 모호한 다중 식별값, 열이 어긋난 표, 과대 레코드는 확정 연결에서 제외합니다. 원문 내용·전화번호·실제 메시지/서비스 번호는 비식별 JSON에 내보내지 않습니다.

### Job·성능

기존 실행 주기/공백/RUNNING/ABNORMAL, P95, 단계별 처리시간, 관측 처리율은 유지합니다. 세부 화면 두 개를 Job·성능 안으로 모았습니다. DB 실제 적체량은 로그에서 추정하지 않으며 기존 수동 숫자 관측은 세션 한정입니다.

정상 구간 비교는 **같은 분석의 다른 시간대**만 선택합니다. 별도 Agent·HA·Master/Standby 입력/비교 UI는 제거했습니다. 원래 로그의 `HA_RECEIVE_RESULT` 같은 Job 이름은 실제 관측이므로 지우거나 분석에서 제외하지 않습니다.

## 자료 보정과 이전 분석

이전 저장 분석은 새로운 오류 작업/의미 필드가 없을 수 있습니다. **자료 점검 → 원본 재해석 (기존 분석 보존)**으로 현재 세션용 결과를 만들 수 있습니다. 로그 기준 날짜와 조회 구간은 서로 다른 설정입니다. 날짜 없는 자료도 오류 내용/메시지 번호 검색은 가능하지만 시간별 Job·처리율은 실제 기준 날짜 확인 전 계산하지 않습니다.

재해석은 원본 해시를 확인한 뒤 임시 비식별 이벤트를 만들며 기존 manifest/events.jsonl·보고서·문의·사례를 변경하지 않습니다. 세션 종료 후에는 다시 실행해야 합니다. 전체 기존 보고서를 영구 갱신하려면 4 내보내기의 명시적 재분석을 사용하세요. 자동 마이그레이션/삭제/원본 덮어쓰기는 없습니다.

## 디자인·검증 경계

Google Stitch의 실제 데스크톱 요약·자료 가져오기 화면을 먼저 생성했습니다. 원본 CSS 토큰/오류 카드/근거 패널을 재사용하고 실제 데이터·네이티브 입력·버튼에 연결했습니다. 기본 화면과 상세 성능 화면은 같은 색·글꼴·테두리·간격을 사용합니다. 모바일 전용 화면은 없습니다. 가상 예시 숫자는 제품에 넣지 않습니다.

운영 명령·자동 재발송·DB/Redmine 쓰기·외부 AI 로그 전송은 없습니다. 고객 로그와 내부 인계/검증 원본은 공개 저장소에 포함하지 않습니다. 검증은 합성 데이터와 제공된 로그 형식에 기반하며, 현재 고객사의 모든 커스텀 로그와 Windows 네이티브를 검증했다는 의미는 아닙니다. 공개 push/정식 릴리스는 별도 승인 후 수행합니다.
