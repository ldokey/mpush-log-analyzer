# MPushAgent Log Analyzer — V4 분석 워크벤치

## 목적과 데이터 모델

기존 V3는 동일 유형의 여러 문제를 Finding 하나로 요약하고 근거를 최대 5건만 대표 보관한다. V4는 **Finding(유형별 요약)** 과 **Occurrence(개별 정규화 이벤트)** 를 분리해 전체 실행 기록을 검색하고, 선택한 이벤트에서 Evidence(원본 파일 별칭·줄번호·시각)를 확인하도록 확장했다. 새 서버·외부 AI·DB는 도입하지 않았다.

정규화 이벤트는 원본 로그의 모든 줄과 동일하지 않다. 인식되지 않은 일반 텍스트 행은 전체 이벤트 탐색에도 나타나지 않는다. 로그의 읽은 줄 수와 이벤트 추출 건수의 비율은 파싱 성공률이 아니다.

## 조사 흐름

1. 분석 대시보드에서 작업을 선택한다. 상단의 **분석 메뉴** 6개 중 하나를 고른다. 선택하지 않은 화면은 백그라운드에서 JSONL을 조회하지 않는다.
2. 종합 현황의 시간대 그래프 아래에서 구간을 정하고 **선택 시간대의 전체 이벤트 조회**를 누르면 해당 날짜·시각 필터가 전체 이벤트에 전달된다.
3. 상세 목록에서 필터·정렬·페이지·표시할 열을 선택한다. 25/50/100/200건씩 조회할 수 있다.
4. 한 행을 선택하면 허용된 구조화 속성이 모두 나타난다. 마스킹 원본과 전후 120초 관련 이벤트는 사용자가 선택할 때만 추가 조회한다.
5. 현재 페이지에서 선택한 안전한 열만 CSV로 저장할 수 있다. 원본 로그의 전체 내보내기가 아니다.

## 구분해서 해석할 사항

- Finding 개수는 지연/오류 **실제 발생 횟수**와 다르다. 개별 지연 발생은 Job/DB 화면에서 절대 기준 초과 필터로 검색한다.
- 절대 기준 초과 조회는 설정된 하한을 만족한 개별 이벤트를 뜻한다. Job의 비교 중앙값을 적용한 최종 탐지 판정과 다를 수 있다.
- Job의 기록 시각(완료), 로그상 시작, 소요시간 역산 시작은 구분한다. 로그 근거가 부족하면 임의 날짜를 만들어내지 않는다.
- RESPONSE_CODE=S는 CNS 발송 요청 수락이지 최종 수신 성공이 아니다.
- DB Laptime 지연·SOCKET/HTTP 단계 지연·헬스체크 기록 공백만으로 DB Lock·네트워크 장애·Agent 종료를 확정하지 않는다.
- 서로 다른 Agent/서버를 합쳐 분석하지 않는다. 업무상 인과관계는 추가 증거와 별도 검증이 필요하다.

## 대용량 검색·보안

- 서버 측 스트리밍 필터를 적용하고 기본 조회는 50건/페이지다. 오래된 시각순에서는 전체 정규화 이벤트를 임의로 자르지 않는다.
- 최신순·처리시간 긴 순은 메모리 제한을 위해 정렬 결과 **상위 20,000건 범위**까지 페이지로 이동한다. 전체 조건 일치 건수는 별도로 표시한다. 더 먼 과거의 기록은 시간 조건을 좁히거나 오래된 순으로 조회한다.
- 날짜가 없는 이벤트는 시간 검색에서는 제외되지만 전체 기간 검색에서는 표시한다.
- 새로운 파일 기반 인덱스나 서버 DB는 도입하지 않았다. 대용량 파일 반복 조회의 실측 성능이 부족한 경우 별도 슬라이스로 로컬 인덱스를 검토한다.
- 화면과 CSV에는 허용된 숫자, ISO 시각, Job 토큰, SQL 명령 종류, 상태, 오류 클래스만 투영한다. SQL 본문·메시지·비밀번호·인증정보·개인 원본파일명·오류 원문은 직접 포함하지 않는다.
- 원본은 기존 마스킹 및 해시 확인을 적용한다. AI·외부 전달 전에는 담당자가 재검토해야 한다.

## 별도 검증이 필요한 사항

원격 Mac 합성 데이터로 구현·검증했다. 사내 Windows 실제 실행/NTFS ACL·백신, 고객사 3.2/3.3 변형 패턴, 실제 300MB 로그 조회 성능은 별도로 검증해야 한다. 공개 GitHub는 자동으로 배포하지 않는다.

Mac Python 3.13, 10MiB 합성 debug 로그 180,788 정규화 이벤트 기준 한 번의 테스트 실행에서 전체 분석 약 3.011초, 기존 대시보드 조회 약 0.583초, V4 전체 이벤트 오래된 순 50건 페이지 약 0.766초, 최신 순 50건 페이지 약 1.061초. 최대 프로세스 메모리 약 171.5MiB로 관측했다. 실제 고객사 DBWrap 로그, Windows 실행, 대용량 반복 조회에서 결과는 달라질 수 있다.
