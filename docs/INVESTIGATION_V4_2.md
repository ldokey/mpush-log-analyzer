# V4.2 장애 조사 워크벤치 — 사용·설계·해석 경계

## 기준 자료와 현재 범위

Notion의 **MPushAgent 로그 분석 프로그램 — 장애 사례 기반 기능 개선·로드맵**(내부 장애 대응 요구사항)와 연결된 로그 구분·증상별 점검 문서를 기준으로 구성했다. 사용자 지시에 따라 **XML과 Agent 2.8은 선택 참고**이며 없어도 핵심 기능이 동작한다.

기존 V3.1/V4/V4.1 기능과 문의·해결 기록은 유지한다. 상단의 분석 대시보드에서 **장애 조사**를 선택하면 7개 조사 기능을 사용할 수 있다. 개발본 구현이며 기존 Public v4.0.0이나 사용자 Windows 설치가 자동 갱신되는 것은 아니다.

## 1. 장애 구간 타임라인

조사 구간은 KST 기준 **[시작 포함, 종료 미포함)** 이다. 날짜 없는 로그에 오늘 날짜를 임의 부여하지 않는다. 기간 상한은 31일이며, 짧은 장애 구간으로 좁히는 것을 권장한다.

info / err / job / debug / dbwrap을 동일 시간축에 보여준다. 위의 점은 시간 버킷별 이벤트 밀도, 아래 표는 개별 사건이다. 0건 버킷에 사건 점을 그리지 않는다. 인식된 이벤트가 없는 시간대를 곧 장애로 표시하지 않는다.

Job 구간은 로그상 시작이 있으면 그것을, 없으면 완료시각에서 소요시간을 뺀 **역산 추정값**을 사용한다. 서로 다른 Job의 시간적 중첩을 보여주지만 선후 인과관계·Lock을 단정하지 않는다. SELECT 단계에는 조회뿐 아니라 선점 처리가 포함될 수 있다.

표·상세 화면은 기존 V4.1의 로컬 원본명/상대경로와 file_id를 사용한다. 근거 확인은 기존 원본 해시 검증과 마스킹 뷰를 재사용한다.

## 2. 예외 원인 체인

err 뿐 아니라 info/debug의 예외도 연속 스택 구조로 수집한다. 첫 번째 클래스만 남기던 처리에서 root / Caused by / Suppressed / 별도 언급을 구분하도록 확장했다. 같은 시각을 반복해서 찍은 명시적 Caused by 행도 같은 스택으로 연결한다.

예: SQLTimeoutException → CommunicationsException → SocketTimeoutException. 화살표는 원문의 명시적 원인 연결이며 운영 장애 원인의 최종 확정은 아니다. Suppressed가 섞이면 하나의 직선 원인처럼 보이지 않게 관계를 별도 표시한다. 스택 프레임의 고객 패키지·원문 메시지·주소·인증정보는 결과에 보관하지 않는다.

동일 파일의 동일 체인을 묶어 반복 기록 수, 최초/최종 시각, 명시적으로 기록된 Job, 근거 행을 제공한다. 반복 로그 수와 실제 독립 사고 수는 다르다. 서로 다른 파일에 복제된 오류를 자동으로 같은 사건 또는 별개의 사고로 확정하지 않는다.

**과거에 분석해 둔 결과에는 새 체인이 없을 수 있다.** 해당 경우 안내를 표시한다. 내보내기·관리에서 **원본 검증 후 재분석·사례 매칭·보고서 갱신**을 실행하면 새 파서가 적용된다. 이전에 잃은 하위 예외를 기존 요약만으로 만들어내지 않는다.

## 3. 정상·장애 비교

담당자가 정상 기준 분석 및 기간을 선택하고 같은 Agent·비교 가능한 수집 조건인지 확인한다. 두 구간은 **동일 길이**여야 한다. 프로그램이 해당 기준 구간의 정상 상태를 보증하지는 않는다.

Job/SQL별 기록 수, 처리대상, 평균, P50, P95, 최댓값, P95 배율 및 단계별 시간 통계를 비교한다. 한쪽만 관측되는 항목은 다른 쪽을 0으로 채우지 않고 관측 없음으로 둔다. 부분 로그, 미상 버전, 기간 내 이벤트 부재를 함께 표시한다.

P50/P95는 선형 보간으로 계산하며 전체 표본을 보관하지 못한 경우 빈 값으로 남긴다. 일부 표본의 백분위를 전체 값으로 표현하지 않는다. 평균·최대·횟수는 별도 집계한다.

구간 내 완료 기록의 작업대상 합계/구간 길이는 관측 지표이지 최종 성공 TPS, 지속 처리능력, 현재 DB 적체, 전체 완료예정 시각이 아니다.

## 4. 주기·기록 중단

세 가지 근거를 나란히 구분한다.

- 선택 구간의 관측 완료·헬스체크 간격과 RUNNING 건너뜀
- 전체 제공 자료에서 마지막으로 인식된 이벤트와 담당자가 입력한 실제 수집시각
- info의 예약 등록, Agent 기동/종료 기록 및 별도 담당자 PID·재시작 관측

예를 들어 01:00 일일 예약과 11:21 Agent Exited는 다른 기록이다. 예약 시각과 기록 공백이 맞아도 원인 확정으로 처리하지 않는다. 마지막 정규화 이벤트가 원본 전체 텍스트의 최종 행과 같은 의미도 아니다.

일정한 간격의 단순 Quartz 표현식만 제한적으로 주기값을 읽는다. 일반 cron 전체 평가기는 아니다. 확정할 수 없는 표현식, 변경·충돌한 예약은 숫자 주기로 추정하지 않는다. 관측 간격 기준도 충분한 양의 표본과 안정성 조건을 만족할 때만 사용한다. 다른 파일 경계를 가로질러 누락 구간을 추정하지 않는다.

## 5. 메시지별 추적 — 제한적 명시 기록 지원

추적 버튼을 누른 경우만 원본 해시를 검증하고 로컬 원본에서 식별 필드를 읽는다. 동일 레코드에 **SERVICE_SEQNO와 MESSAGE_SEQNO가 명시된 경우**만 연결한다. 필터값은 로컬 화면 입력이며 결과는 세션별 가명으로 표시한다. 원문 ID·본문·SQL을 추적 결과에 보관하거나 자동 내보내지 않는다.

명시된 발송 요청, 선점, 파일 생성, 암호화, 전송, 수락, 결과 수신, DB 이관 **표지의 관측 여부**를 기록한다. 표지가 보였다고 그 단계가 성공했다고 단정하지 않는다. 빠진 단계는 미관측이다. 최종 배송은 별도 근거가 없으므로 미확인으로 유지한다.

SQL의 RESPONSE_CODE='S' 등 조건값은 실제 수락/상태 전이가 아니므로 별도로 구분한다. SEND_FLAG는 기록된 코드만 보여주며 원문에 제공되지 않은 상태코드 사전을 만들어 적용하지 않는다. SQL ? 바인드 순서나 시간적 근접성으로 식별값을 추측하지 않는다. 복수 식별값·본문에 포함된 키·과대 레코드는 연결에서 제외한다.

같은 메시지 번호라도 서비스가 다르면 다른 가명이다. 반복 요청/결과가 있으면 임의로 한 요청과 한 결과를 짝지어 지연을 계산하지 않는다. R00/B00은 명시된 JOB_TYPE만 집계한다. Job 이름으로 실시간/배치 유형을 추정하거나 다른 Agent의 처리량을 합산하지 않는다.

원문 Notion은 모든 고객사 커스텀 로그의 문법/바인드 위치를 제공하지 않는다. 따라서 이 기능은 **명시적 필드·단계 표지가 있는 형식의 제한적 추적**이며 모든 발송 경로를 자동 복원하는 기능이 아니다.

## 6. 운영 관측과 선택 참고자료

PID 상태·확인시각, 재시작 여부·시각, 참고 버전, 담당자 메모는 별도의 private 파일에 저장한다. 수정 버전 충돌을 검출하며 기존 기록을 조용히 덮어쓰지 않는다. 담당자 관측은 로그의 자동 판단과 구분한다.

Agent 2.8은 **2.8-reference** 표시만 제공한다. 2.8 전용 파서와 현장 호환성 검증 완료를 뜻하지 않으며 3.2/3.3 규칙을 2.8에 자동 확정 적용하지 않는다. 3.2/3.3도 사용자 선언 버전과 실제 현장 빌드 확인은 다르다.

선택 XML은 UTF-8, 512KiB 이하, 노드/깊이/텍스트 제한 하에 알려진 Job 이름·cron/debug 값만 요약한다. DTD/엔터티·외부 참조는 차단한다. 알려진 명시 속성/태그를 읽을 뿐 모든 devon-core/quartz 스키마를 해석하지 않는다. XML이 없거나 해석되지 않아도 핵심 분석은 계속 가능하다.

제공된 설정의 debug 여부와 debug 파일 제공 여부, XML 예약과 info에서 관측된 예약 표현식을 비교한다. 설정의 배포 시점·실제 활성화 여부는 추가 확인 사항으로 남긴다. HA 관련 주석에서 이름이 보인다는 이유로 HA 중단을 단정하지 않는다.

## 7. 추가 증거·회신 초안

관측 사실 / 가능한 원인 / 필요한 추가 증거 / 해석 한계를 분리해 보여준다. 원본 file_id와 근거 행을 연결한다. 프로세스·TCP·DB의 읽기 전용 점검 예시를 제공하지만 **명령·SQL을 실행하지 않는다**. 실제 환경·권한·조회 부하는 담당자가 판단한다.

담당자가 검토 확인을 한 경우 회신 초안 TXT를 생성한다. Redmine/메일/외부 AI로 자동 전송하지 않는다. 기존 문의의 조치·해결 기록을 자동 승인하거나 원인 확정 상태로 바꾸지 않는다.

## 안전·성능 제한

타임라인은 페이지 방식으로 전체 조건 일치 건수를 집계한다. 예외 그룹은 300개, 그룹별 대표 근거 100개, 체인 노드 24개까지 보관하고 생략을 표시한다. Job 구간은 500개, 중첩 표시는 100쌍까지다.

통계는 분포별 50,000개, 전체 숫자 표본 250,000개 상한을 둔다. 주기 계산은 시퀀스별 50,000개, 전체 100,000개까지 보관하며 제외 수를 표시한다. 한도에 도달하면 기간을 좁혀 조회한다. 메시지 그룹은 5,000개, 이벤트 표시는 20,000개이며 표시 상한을 넘기면 경고한다. 표시 생략을 완전한 전수 분석으로 표현하지 않는다.

표시용 캐시는 해당 세션의 계산 결과만 보관하고 입력 manifest·이벤트 파일 변경 시 무효화한다. 원본 고객 로그를 외부 서비스에 전달하거나 운영 DB를 연결하지 않는다. 새 필수 패키지는 추가하지 않았다.

## 후속 설계 범위 (이번 자동 구현 아님)

V5 다중 Agent/HA 분석은 서버별 Agent ID, 로그 시각 오프셋 근거, 서비스 겹침, Active/Standby 관측, 전환 근거가 있어야 한다. 이 조건이 없는 상태에서 한 타임라인으로 합쳐 처리량을 더하거나 장애 원인을 자동 연결하지 않는다.

실제 Windows/NAS, 실제 고객사 원본·커스텀 메시지 형식, 임의 스케줄 문법, 대규모 복합 압축의 현장 검증은 합성 테스트와 별도다. 이번 변경은 공개 배포/Windows 설치 갱신과도 구분한다.
