# MPushAgent Log Analyzer v4.2.0

**MPushAgent 3.2 / 3.3 로컬 기술지원 로그 분석기**
**V3.1 + V4 + V4.1 + V4.2 통합 공개 배포판**

고객사에서 제공받은 Agent 로그를 로컬 PC에서 읽고, **Redmine 문의별 자료 관리 → 로그 수집·분석 → 장애 구간 조사 → 원인 후보·조치·검증 기록 → 검토된 해결 사례**로 이어지는 업무를 지원합니다.

> **중요:** 이 프로그램은 운영 Agent, 서버, 데이터베이스 또는 Redmine을 직접 제어하지 않습니다. 원본 로그·고객 식별정보·인증정보를 외부 AI로 자동 보내지 않습니다. 모든 분석은 제출된 자료의 관측 범위에서 수행합니다.

## V4.3 개발 브랜치 — 실행·발송·성능 진단 (미배포)

**이 브랜치에서만 제공하는 개발 기능이며, 기존 공개 릴리스 v4.2.0은 그대로 유지됩니다.** Windows 설치본이 자동으로 갱신되지 않습니다.

**분석 대시보드 → 실행·발송·성능**에서 세 가지 데스크톱 화면을 사용합니다.

- **Job 실행 진단:** 정상 기준 대비 소요시간(P95), 실행 공백·RUNNING 반복, 지연 집중 및 원본 근거 확인
- **메시지 결과 추적:** 로컬 원본 조회 동의 후 가명 메시지 검색, 원 발송·문자 대체 성공/실패, 미확인·충돌 및 단계별 근거
- **처리 성능·대기량:** Job별 관측 처리율·단계별 시간, 담당자가 별도로 확인한 DB 대기량 수동 입력·순증감

**제외:** 다중 Agent/HA, 설정파일 분석 확대, 버전별 호환성 확대, 모바일, 자동 재발송·DB/Redmine 쓰기. 최종 성공은 명시적인 결과 수신 기록의 CODE1/CODE2로만 판정하며, 요청 수락 `RESPONSE_CODE=S`는 최종 성공이 아닙니다. 관측 공백은 Agent 종료 확정 근거가 아닙니다.

### V4.2 — 장애 조사 워크벤치

기존 **분석 대시보드 → 장애 조사** 메뉴에서 이용합니다.

- **5종 로그 통합 타임라인:** info / err / job / debug / dbwrap의 시간대별 사건, Job 실행 구간·중첩 및 원본 근거 조회
- **Java 예외 원인 체인:** 같은 스택의 root / Caused by / Suppressed 관계, 반복 기록 수, 최초·최종 관측시각
- **정상·장애 시간대 비교:** 같은 길이의 두 구간에서 Job/SQL 기록 수·처리시간 평균/P50/P95/최댓값·단계별 소요시간
- **Job 정체·기록 공백 조사:** 관측/등록 주기, RUNNING 실행 건너뜀, 마지막 로그·수집시각·기동/종료 기록 구분
- **메시지별 명시 기록 추적:** 같은 레코드의 MESSAGE_SEQNO + SERVICE_SEQNO 식별 필드와 단계 표지를 연결해 세션별 가명으로 표시
- **추가 자료 안내·회신 초안:** 관측 사실 / 가능 원인 / 필요한 추가 증거 / 해석 한계를 구분해 검토용 텍스트 제공
- **선택 참고자료:** agent.ini에서 안전한 설정 정보 조회, 선택 XML의 알려진 주기/debug 설정 비교, 운영자 PID·재시작 관측 메모
- **Agent 2.8 및 XML은 선택 참고입니다.** 2.8 전용 파서의 현장 호환성은 검증된 상태가 아닙니다.

상세: [V4.2 장애 조사 가이드](docs/INVESTIGATION_V4_2.md)

## 설치·실행

### Windows 10/11 (Python 3.13, 64비트)

1. [v4.2.0 릴리스](https://github.com/ldokey/mpush-log-analyzer/releases/tag/v4.2.0)의 ZIP을 내려받아 **C: 로컬 폴더**에 압축을 풉니다.
2. PC에 Python 3.13 x64가 설치되어 있는지 확인합니다.
3. **START_WINDOWS.bat**를 더블클릭하거나 PowerShell에서 다음을 실행합니다.

~~~powershell
cd "C:\Tools\mpush-log-analyzer-v4.2.0"
.\START_WINDOWS.bat
~~~

4. 브라우저에서 <http://127.0.0.1:8501>로 접속합니다. 종료는 실행 창에서 **Ctrl+C**입니다.

**독립 실행형 EXE가 아닙니다.** 최초 실행에서는 필수 Python 패키지 설치에 인터넷/사내 프록시가 필요할 수 있습니다. 새 버전을 **별도 폴더에 풀면 .venv를 다시 생성**합니다. 기존 폴더에서 소스만 갱신할 경우 .venv를 보존할 수 있으나, 반드시 기존 **workspace/**와 **knowledge/**를 먼저 백업하세요. 기존 설치본을 지우거나 덮어쓰기 전에 작동을 확인하는 것이 안전합니다.

**원본 고객사 로그는 사용자가 등록한 폴더에서 선택해 읽습니다.** 분석 저장 폴더와 실행 환경은 개인 로컬 디스크를 권장하며, 네트워크 드라이브 접근 권한은 실행 PC·Windows 계정에 따라 다릅니다.

설치 문제: [Windows 가이드](docs/WINDOWS_QUICK_START.md)

### macOS / Linux (Python 3.13)

~~~bash
python3.13 -m venv .venv
.venv/bin/python -m pip install -r requirements-dev.txt
bash scripts/run_local.sh
~~~

실행 후 <http://127.0.0.1:8501> 접속.

## 고객지원 업무 흐름

1. **문의·해결 기록**에서 Redmine 이슈를 확인하거나 등록합니다.
2. **자료 가져오기**에서 지정 폴더 또는 로그/압축파일을 선택하고 **동일 Agent 인스턴스인지 확인**한 뒤 분석합니다.
3. **분석 대시보드**의 전체 이벤트·Job·DB 및 **장애 조사**에서 근거 시각과 행을 찾습니다.
4. **문의·해결 기록**에 관측 사실 / 원인 후보 / 실제 조치 / 검증 결과 / 다음 확인사항을 작성합니다.
5. 재사용 가능한 비식별 사례만 **사례 라이브러리**에서 검토·승인합니다.
6. **내보내기·관리**에서 비식별 보고서·AI 요약 등을 내보냅니다. 내부 답변용 TXT는 별도로 사용자가 검토합니다.

## 정확성 및 보안 제한

- 전체 이벤트는 **정규화된 로그 사건의 전체**이며, 인식하지 못한 원본 텍스트 행까지 포함하지 않습니다.
- **RESPONSE_CODE=S는 요청 수락**이지 최종 수신 성공이 아닙니다.
- DB Laptime/SELECT/SOCKET 지연으로 Lock·네트워크 장애·Agent 종료를 단정하지 않습니다.
- 정상일/장애일 비교에는 **같은 Agent·기간 길이·자료 완전성** 검토가 필요합니다.
- 메시지 추적은 **명시된 두 식별값이 같은 레코드에 존재할 때만** 연결합니다. 임의 SQL 바인딩/미기재 상태를 추측하지 않습니다.
- **자동 다중 Agent·HA 합산과 전역 원인 추론은 미구현**입니다.
- 원본 로그는 해시로 검증하고, SQL·메시지 원문·자격 증명은 분석 결과에 직접 포함하지 않습니다.
- Redmine·이메일·외부 AI로 로그 원문을 자동 업로드하지 않습니다.

## 테스트 및 배포 범위

- macOS + Python 3.13, **합성 입력 기준 229개 자동 테스트 통과**. 공개용 정제 사본도 별도 테스트합니다.
- Windows 10/11 실제 실행, 고객사 원본 로그, NAS/ACL/백신 환경, 2.8 및 고객사별 커스텀 로깅의 현장 호환성은 별도 검증 대상입니다.
- 합성 10MiB debug 로그 180,788개 이벤트의 분석/조회 성능은 실제 고객사 파일과 다를 수 있습니다.
- 공개 ZIP에는 실행 코드·설명서·합성 테스트만 포함합니다. .venv, 원본 고객사 로그, 개인 workspace, 내부 개발 인계 문서는 포함하지 않습니다.

~~~bash
.venv/bin/python -m pytest -q
.venv/bin/python -m scripts.benchmark_synthetic --megabytes 10
~~~
